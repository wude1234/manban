业务场景：卡车司机的“智能接单大脑”
赛题聚焦月度接单决策优化，背景源自广东真实物流业务，选手需构建智能体实现三重目标：1收益最大化：不仅要算清单次接单利润，更要平衡路线成本、运输惩罚（比如超时送货扣钱）2泛化能力与强感知：司机可能突然变更需求（如临时要去广州接家人），AI 需实时捕捉动态偏好3系统约束：运输时间、载重载方、货源匹配等硬性规则不能破，但本次比赛尽可能简化业务复杂性，构造更清晰数据环境
关键难点：动态偏好无规律：突发情况占比超 30%，传统规则引擎完全失效
场景真实性：要素脱敏后仍保留货源波动、路线货量密度等真实特性，仿真环境高度还原实战

如何把「规则脚本」改成更像 Agent 的决策器
本场主要分享了将货运调度「规则脚本」升级为决策 Agent 的实战经验，核心是跳出短视贪心，构建更稳定的三层智能决策体系。路同学指出，Agent 不应只是「算收益的财务计算器」，还需兼顾长期收益、司机偏好与位置价值。第一层将口语化偏好做解析，用大模型处理比纯正则更灵活；第二层从可行性、净收益、单位时间收益、位置价值等维度评估订单；第三层为 Agent 引入状态记忆与动作选择，支撑连续路径上的决策。大模型不替代规则，仅在订单分数接近、收益与偏好发生冲突时做仲裁，并以结构化输入保障输出稳定。分享中还强调：先保证动作合法、格式稳定；偏好既不硬编码，也不忽视罚分边界；重视单位时间收益；做好异常兜底。整体思路是规则保稳定、大模型增弹性、记忆保连续、评分可解释，从而在长期仿真中实现更稳健的调度表现。
把「规则脚本」拆成偏好保护、订单评分、状态记忆三层，再让大模型只在分数接近、偏好冲突时做仲裁，模型定位和工程边界都讲得很清楚。



周同学围绕卡车司机连续找货决策任务，分享了对赛题的理解与团队实践。他认为，这道题并不是简单的货源排序，而是在未来不可知、当前局部可见、动作影响后续、偏好改变目标四类约束下，做长期收益优化。团队将方案设计为受控 Agent：偏好编译把自然语言转成可执行策略；司机私有 Memory 记录本轮合法观察到的市场摘要；Route Plan 比较一段路线而不只是一单；LLM Critic 在关键分叉做受控评审；最后由安全执行层统一输出合法动作——观测、规划与决策均在合法接口内完成。分享末尾还整理了查询成本如何权衡、LLM 与规则如何分工、Memory 怎样用才不过度依赖旧信息、分数停滞时如何避免陷在局部最优，以及如何用事后回放对照分析差距等体会，供各位选手参考。

用四个难点串起 Route Plan、Memory、偏好编译和受控 Critic，尤其是「接一单等于选一段路线」这一点，把讨论从单笔收益拉到了路线级权衡

陈同学的分享聚焦司机连续找货 Agent 赛题，围绕避免过拟合、划清边界、跳出局部最优、规范版本管理四个方面展开。赛题本质是NP-hard的序列决策问题：纯贪心容易陷入短期最优，过度拟合单一司机或规则又会损害泛化。分享提出分层 Agent 思路——感知层、规划层借助 AI 做模糊输入的结构化与高层策略判断，执行层的打分、排序、约束校验回归确定性代码，LLM 只做感知、规划等不可替代的事，各司其职。决策上不只靠「贪心选高价单」，还需主动空驶、合理休息，才更有利于月度全局表现。工程上强调用 Git 管理代码，版本清晰、模块化迭代，便于调优与复盘。

作弊规则是什么样子的?
最后一周评测司机数据没有公开，所以也放宽了作弊检查的规则，之前只要是硬编码偏好规则的都认为是作弊，现在只检查有没有在代码里写死货源id。

能否设置偏好的结构化类型?
可以，但是需要提醒的是，真实世界中司机的个性化偏好是枚举不完的，结构化无法覆盖所有场景，要考虑到不能覆盖的偏好应该怎么处理。


夏赛数据也不公布吗?有什么变化?
是的，复赛数据不对外发布，并且货源数据也不公布。复赛时选手将完全在未知数据上进行比赛，可以在已发布的初赛数据集上继续调试。
